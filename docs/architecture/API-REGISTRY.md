# API registry — proposed architecture

- Status: **Proposed; not accepted**
- Tracking: [issue #12](https://github.com/vsimko/gfabasic-rust/issues/12), [API profiles #5](https://github.com/vsimko/gfabasic-rust/issues/5), [Atari API reference #25](https://github.com/vsimko/gfabasic-rust/issues/25), [registry validation #55](https://github.com/vsimko/gfabasic-rust/issues/55), [conformance corpus #42](https://github.com/vsimko/gfabasic-rust/issues/42)

## 1. Purpose

The registry describes language and platform API declarations in a machine-readable form so that parsing/semantic analysis, profile selection, runtime mapping, reference documentation and conformance tests do not drift apart.

A registry entry is evidence-backed metadata. Its presence does not mean the feature is implemented or supported.

## 2. Proposed source-of-truth model

**Proposal for review:** a checked-in declarative registry is canonical for declaration metadata. Rust code implements behavior behind stable IDs; it must not independently redefine spelling, syntax availability, signatures or profile membership.

- Registry owns declaration identity, syntax shape, types, dialect/version/profile availability, evidence, support classification and links to tests.
- Rust owns executable semantic/runtime behavior and provides implementation handlers referenced by stable IDs.
- Reference documentation can be generated from registry metadata plus authored explanatory material.
- Tests remain independent fixtures linked from the registry. Expected results must not be generated by the implementation being tested.
- Research-only, unsupported, unsafe and unknown entries are allowed, provided their status is explicit.

This is a proposal under issue #12, not an accepted ADR. Serialization format and directory layout remain open.

## 3. Required declaration fields

| Field | Required | Purpose |
|---|---|---|
| `id` | Yes | Stable globally unique identifier, independent of spelling |
| `name` | Yes | Canonical source spelling |
| `kind` | Yes | Statement, function, procedure, operator, special form, constant, variable or structure |
| `syntax` | Yes | One or more structured parse forms |
| `availability` | Yes | Dialect, version range and required API profile(s) |
| `signature` | Yes | Ordered parameters, optionality, mode, type and return type |
| `semantics` | Yes | Contract, side effects, errors, lifecycle and edge cases |
| `evidence` | Yes | Source ID, page/section, evidence state and notes |
| `implementation` | Yes | Runtime/compiler handler ID or explicit none |
| `support` | Yes | Per-target support classification |
| `tests` | Yes | Test IDs or explicit pending reason |
| `docs` | Yes | Reference path and section anchors |
| `status` | Yes | Research, proposed, verified, accepted, deprecated or disputed |

Do not reduce syntax to a display string. The model must express statement/expression context, overloads, optional/repeated arguments, argument passing modes, type suffixes and special grammar.

## 4. Syntax and type model

The type vocabulary should include integer widths, real/numeric, string, boolean-like values, arrays, procedures/functions, pointers/addresses, target-specific records and unresolved/opaque values. GFA storage semantics must come from source evidence, not host Rust types.

The syntax model must distinguish required/optional/repeated parameters, value/reference/VAR/array/pointer passing, multiple overloads, version-specific forms, statement versus expression context and special grammar that is not an ordinary function call.

## 5. Example declarations

The following TOML-like examples illustrate the proposed model only. They are not accepted declarations or code-generation input.

### 5.1 Core expression function

```toml
id = "gfa.core.timer"
name = "TIMER"
kind = "function"
status = "proposed"

[[availability]]
dialect = "atari-st-gfa-basic"
versions = ["2.x", "3.0"]
profiles = ["core"]

[[syntax]]
form = "call"
context = ["expression"]
arguments = []

[signature]
returns = "integer"

[semantics]
summary = "Returns elapsed system ticks."
notes = ["The selected Atari source documents 200 ticks per second."]

[[evidence]]
source = "ATARI-GFA-BOOK-1988"
pages = "chapter 12, pp. 393–452"
state = "book-documented"

[implementation]
handler = "runtime.core.timer"
state = "unimplemented"

[[support]]
target = "linux-x86_64"
classification = "unsupported"

tests = []
docs = ["docs/reference/atari-gfa-basic-3.0.md"]
```

### 5.2 Atari statement with alternative syntax

```toml
id = "gfa.atari-st.window.open"
name = "OPENW"
kind = "statement"
status = "research"

[[availability]]
dialect = "atari-st-gfa-basic"
versions = ["3.0"]
profiles = ["atari-st"]

[[syntax]]
form = "call"
context = ["statement"]
arguments = [
  { name = "window_number", type = "integer", required = true },
  { name = "center_x", type = "integer", required = false },
  { name = "center_y", type = "integer", required = false }
]

[[syntax]]
form = "call"
context = ["statement"]
arguments = [
  { name = "window_number", type = "integer", required = true, marker = "#" },
  { name = "x", type = "integer", required = true },
  { name = "y", type = "integer", required = true },
  { name = "width", type = "integer", required = true },
  { name = "height", type = "integer", required = true },
  { name = "attributes", type = "integer", required = true }
]

[signature]
returns = "none"

[semantics]
summary = "Opens a predefined GEM window or defines and opens a window."
side_effects = ["Creates or activates an AES/GEM window.", "Acquires a window handle."]
resource_lifecycle = "The window must be closed through the matching GFA/GEM operation."

[[evidence]]
source = "ATARI-GFA-BOOK-1988"
pages = "pp. 476–479"
state = "book-documented"

[implementation]
handler = "runtime.atari_st.window.open"
state = "unimplemented"

[[support]]
target = "linux-x86_64"
classification = "unsupported"

tests = []
docs = ["docs/reference/atari-gfa-api.md#3-gfa-level-gemaes-wrappers"]
```

The examples show why functions and statements need distinct syntax/context metadata and why a statement may have multiple argument forms.

## 6. Version and profile matching

- Dialect identity and API profile are separate.
- Version ranges must be explicit. Do not treat V2.xx as one exact release unless evidence supports it.
- An entry requiring `atari-st` is unavailable when that profile is not selected, even if the output target is Linux.
- A profile dependency must be source-backed.
- Conflicting visible names across enabled profiles must produce deterministic diagnostics; never resolve silently by file order.
- Version-specific overloads remain separate syntax alternatives or separate declarations linked by a shared concept ID.

## 7. Evidence and support states

Evidence and implementation support are independent.

Evidence states: `book-documented`, `primary-reference-cross-checked`, `runtime-observed`, `inferred`, `disputed`, `unknown`.

Support classifications: `implemented`, `partial`, `adapter-backed`, `emulated`, `unsupported`, `unsafe-disabled`, `unknown`.

A hardware call may be well documented while remaining `unsafe-disabled`. A documented command remains unsupported until compatible behavior and tests exist.

## 8. Validation rules

The validator (issue #55) should reject or flag:

1. Missing or duplicate stable IDs.
2. Duplicate names whose availability overlaps without an explicit overload/conflict rule.
3. Invalid version ranges or unknown dialect/profile identifiers.
4. Functions without return metadata or statements without statement syntax.
5. Parameters with missing types, invalid optional ordering or inconsistent overload arity.
6. Unresolved implementation handler IDs.
7. Implemented/partial support without an implementation mapping.
8. Supported declarations without source evidence and conformance tests.
9. Broken documentation anchors or test IDs.
10. Atari/Amiga declarations assigned to the wrong profile.
11. Unsafe operations without explicit safety classification.
12. Syntax alternatives that collide in the same enabled dialect/version/profile.

Research entries may omit implementation and tests only when the omission is explicit and support is not claimed.

## 9. Proposed repository layout

```text
api/
  registry/
    core/
    amiga/
    atari-st/
  schema/
  generated/
tests/
  conformance/
    manifest.toml
    core/
    amiga/
    atari-st/
```

This is provisional; align it with the current Cargo workspace before adoption. Generated files should be reproducible and not manually edited.

## 10. Ownership and workflow

1. Research records the candidate and source pages in the relevant reference.
2. Add a declaration with status `research` or `proposed`.
3. Review spelling, syntax, types, version/profile availability and semantics.
4. Add a focused conformance fixture or record why testing is deferred.
5. Link an implementation only after its handler exists.
6. Validate schema, conflicts, evidence, docs, handler mappings and tests.
7. Mark a declaration `accepted` only after its language/API decision is accepted. Acceptance does not mean implementation is complete.

Before implementing any feature, inspect the corresponding GitHub issues. If no matching issue exists, create it first.

## 11. Open decisions for issue #12

- Canonical serialization format: TOML, YAML or JSON.
- Whether registry metadata is sole source for parser/semantic declarations or validated against Rust declarations.
- Stable ID naming and overload grouping.
- Exact type vocabulary and target pointer/width model.
- Representation of special/context-sensitive syntax.
- Whether generated docs are committed or built only in CI.
- Ownership of evidence updates and review/acceptance status.
- Schema versioning and migration policy.

Do not begin registry implementation from this proposal until these decisions are reviewed and accepted.
