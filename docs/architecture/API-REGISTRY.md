# API registry and declaration source of truth

- Status: **Accepted by [ADR 0006](adr/0006-api-registry.md).** No registry files, schema validator, or generator are implemented yet.
- Tracking: [issue #12](https://github.com/vsimko/gfabasic-rust/issues/12), [validation #55](https://github.com/vsimko/gfabasic-rust/issues/55).

## 1. Purpose and ownership

The checked-in declarative registry is the canonical source for declaration metadata used by parsing/semantic analysis, API profile selection, runtime mapping, reference documentation, and conformance tests.

A registry entry is evidence-backed metadata. Its presence does not mean that the feature is implemented, safe, or supported.

- The registry owns stable declaration identity, spelling, syntax, type/signature metadata, dialect/version/profile availability, evidence, support state, runtime handler IDs, test IDs, and documentation links.
- Rust code implements behavior behind stable registry IDs. It must not independently redefine spelling, syntax availability, signatures, or profile membership.
- Tests remain independent fixtures linked from the registry. Expected results must not be generated by the implementation being tested.
- Generated reference pages may be produced from registry metadata plus authored explanatory material. Generated files must be reproducible and must not be manually edited.
- Research-only, disputed, unknown, unsupported, and unsafe-disabled entries are allowed when their state is explicit.

## 2. Canonical format and layout

Use TOML as the canonical source format. Use one file per logical module/API group, with a versioned schema.

~~~text
api/
├── schema/
│   └── registry-v1.json
└── registry/
    ├── language-core/
    │   └── <module>.toml
    ├── amiga/
    │   └── <module>.toml
    └── atari-st/
        └── <module>.toml
~~~

Each file declares schema-version = 1 and contains one or more declaration records. JSON Schema validates the parsed TOML data model; TOML remains the human-edited canonical source. Schema versions are independent of compiler product versions and runtime ABI versions.

Do not put Amiga or Atari declarations in the language-core namespace. Do not create a core API profile: the language core is not a selectable platform API profile.

## 3. Stable identity and availability

A declaration ID is globally unique, stable across spelling corrections, and independent of version. Use lowercase dot-separated identifiers:

- gfa.language.<module>.<name> for language-core declarations.
- gfa.amiga.<module>.<name> for Amiga API declarations.
- gfa.atari-st.<module>.<name> for Atari ST API declarations.

The declaration record must identify exact source dialect, version availability, and required API profile. Version ranges must use the normalized syntax accepted by the registry schema. Do not use broad labels such as 2.x unless the source evidence explicitly supports the whole range.

A platform API declaration is available only when its required profile is selected. The output target does not enable or disable a source API profile.

## 4. Required declaration model

| Field | Required | Purpose |
|---|---|---|
| id | Yes | Stable globally unique identity |
| name | Yes | Canonical source spelling |
| kind | Yes | Statement, function, procedure, operator, special form, constant, variable, or structure |
| syntax | Yes | Structured grammar alternatives and contexts |
| availability | Yes | Source dialect, exact versions, and required profile |
| signature | Yes | Ordered parameters, optionality, passing mode, type, and return type |
| semantics | Yes | Contract, side effects, errors, resource lifecycle, and edge cases |
| evidence | Yes | Source ID, edition, page/section, evidence state, and notes |
| implementation | Yes | Implementation state and stable handler ID when applicable |
| support | Yes | Per-target support and conformance state |
| tests | Yes | Test IDs or explicit pending reason |
| docs | Yes | Canonical reference path and section anchors |

Do not reduce syntax to a display string. The model must express statement/expression context, overloads, optional/repeated arguments, argument passing modes, type suffixes, and special grammar that is not an ordinary function call.

The type vocabulary must distinguish documented source-language types, arrays, pointers/addresses, procedures/functions, target-specific records, and unresolved/opaque values. Never substitute host Rust types for historical GFA BASIC storage semantics without evidence.

## 5. Evidence, implementation, and support are separate

Do not use one overloaded status field. Each record has independent dimensions.

**Evidence status** describes the source basis: unknown, inferred, disputed, book-documented, primary-reference-cross-checked, or runtime-observed.

**Implementation status** describes code: not-implemented, partial, implemented, or unsafe-disabled.

**Support classification** describes the declared target behavior: supported, partial, adapter-backed, emulated, unsupported, unsafe-disabled, or unknown.

**Conformance status** describes tests: not-tested, passing, failing, or not-applicable.

A well-documented hardware operation may remain unsafe-disabled. A runtime implementation does not establish historical language conformance. A passing unit test does not establish source-language support unless it is linked to a documented rule or trusted reference behavior.

## 6. Illustrative declaration

This TOML example illustrates the accepted data model only. It is not an accepted language declaration or an implementation claim.

~~~toml
schema-version = 1

[[declarations]]
id = "gfa.atari-st.time.timer"
name = "TIMER"
kind = "function"

[[declarations.availability]]
dialect = "atari-st-gfa-basic"
versions = ["3.0"]
profile = "atari-st"

[[declarations.syntax]]
form = "call"
contexts = ["expression"]
arguments = []

[declarations.signature]
returns = "integer"

[declarations.semantics]
summary = "Returns elapsed system ticks."
side-effects = []
errors = []

[declarations.evidence]
status = "book-documented"
sources = ["ATARI-GFA-BOOK-1988"]
printed-pages = ["chapter 12, pp. 393-452"]
notes = ["Verify OCR-sensitive details against the page image before accepting the exact contract."]

[declarations.implementation]
status = "not-implemented"

[[declarations.support]]
target = "x86_64-unknown-linux-gnu"
classification = "unsupported"
conformance = "not-tested"
tests = []

[declarations.docs]
path = "docs/reference/atari-gfa-basic-3.0.md"
anchors = []
~~~

## 7. Version and profile matching

- Dialect identity and API profile are separate.
- Version availability is explicit and evidence-backed.
- A declaration requiring atari-st is unavailable when that profile is not selected, even if the output target is Linux.
- Profile dependencies must be explicit and source-backed.
- Conflicting visible names across enabled profiles must produce deterministic diagnostics; never resolve silently by file order.
- Version-specific overloads remain separate syntax alternatives or separate declarations linked by a shared concept ID.
- Amiga and Atari ST records remain separate even where historical ports share spelling or implementation lineage.

## 8. Validation rules

The validator under issue #55 must reject or flag:

1. Missing or duplicate stable IDs.
2. Invalid schema versions, unknown fields, or missing required metadata.
3. Invalid version ranges or unknown dialect/profile identifiers.
4. Duplicate names whose availability overlaps without an explicit overload/conflict rule.
5. Functions without return metadata or statements without statement syntax.
6. Parameters with missing types, invalid optional ordering, or inconsistent overload arity.
7. Implemented/partial records without a valid implementation handler.
8. Supported declarations without source evidence and conformance tests.
9. Broken documentation anchors or test IDs.
10. Amiga/Atari declarations assigned to the wrong namespace/profile.
11. Unsafe operations without explicit safety classification.
12. Syntax alternatives that collide in the same enabled dialect/version/profile.

Research entries may omit implementation and tests only when the omission is explicit and support is not claimed. The validator must distinguish errors from warnings so that an incomplete research record can be committed without being mistaken for a supported declaration.

## 9. Documentation generation

The registry is canonical for structured facts. Reference pages may combine generated tables/signatures with authored explanatory text, source citations, and examples.

- Generated sections must be clearly marked and reproducible.
- Hand-authored semantic explanations remain reviewable source material; they must not be overwritten by a generator.
- A generated page must retain the registry ID and source provenance.
- CI must detect stale generated output once the generator exists.
- Copyrighted manual text, scans, and substantial extracts must never be copied into generated documentation.

## 10. Ownership and workflow

1. Research records a candidate and source pages in the relevant reference.
2. Add a registry record with evidence status such as inferred, disputed, or book-documented.
3. Review spelling, syntax, types, version/profile availability, and semantics.
4. Add an independent conformance fixture or record why testing is deferred.
5. Link an implementation only after its handler exists.
6. Validate schema, conflicts, evidence, docs, handler mappings, and tests.
7. Mark evidence as cross-checked only after primary-source review; mark support as supported only after compatible behavior and conformance tests pass.
8. Review registry changes with the corresponding language/API documentation and issue.

Acceptance of a registry record does not mean implementation is complete. The registry schema itself is versioned and changes require migration notes.

## 11. Implementation boundary

This ADR accepts TOML as the canonical registry format, the directory structure above, the stable ID convention, and the separated evidence/implementation/support/conformance model. It does not implement the registry, schema, validator, code generator, or any GFA BASIC declaration.
