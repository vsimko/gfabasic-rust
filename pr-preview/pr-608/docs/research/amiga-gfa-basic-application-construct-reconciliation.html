Application-used Amiga GFA BASIC construct reconciliation

Scope and evidence rules

This note reconciles the statement and expression candidates in issue #562 against the existing Amiga inventories and the anonymous 1995 application-listing witness discussed there. The listing is a discovery witness. Its date and coding style suggest a likely GFA-BASIC 3.52 environment, but no exact interpreter build is identified. It is not a runtime test and does not establish 3.5 or 3.52 compatibility.

The supplied GFA BASIC 3.5 Interpreter manual combines a 3.0 base text with a distinct 3.5 addendum. The 1990 German book identifies its main reference as V3.03; its explicitly 3.5-labelled later chapters are a separate evidence scope. Keep those source scopes separate. The inventories cited below are research evidence, not proof of Rust frontend or runtime support.

Fixture status is also separate. The historical application listing is not copied into the repository or corpus. The legacy corpus manifest is marked research_only. PR #568 added an independently authored, exact-form DEFFN/FN probe and recorded native GFA-BASIC 3.52D output. PR #569 proposes a separate UPPER$ probe; its native artifact must be inspected before recording a probe result. No other candidate below is upgraded to native-tested by its occurrence in the application.

External and user-declared boundary

The application's ~Execute, ~OpenLibrary, ~CloseLibrary, ~SetFont, and ~Delay forms are Amiga OS routine calls using the GFA BASIC OS-call convention. They are not built-in BASIC statements or DECLARE FUNCTION … LIBRARY declarations. The sadd helper is application-defined and prepares a string pointer for those calls. Keep the language construct, user-defined helper, and OS/library API namespaces separate.

Summary of remaining work

  • No new built-in declaration is justified for SADD, PEEKL, UCASE$, or MOUSE(...); these are respectively a user-defined helper, a non-canonical spelling for LPEEK, a non-canonical spelling for UPPER$, and a misclassification of the MOUSE statement/state variables.
  • Existing canonical families need no duplicates: MENU, WINDOW, SCREEN, DEFxxx, control-flow constructs, I/O statements, and the listed functions are already represented in the cited inventories.
  • Still unverified as language forms: DECLARE FUNCTION … LIBRARY, SHARED, WINDOW OUTPUT, and PALETTE as a statement. Their absence from inspected passages is not proof of interpreter rejection.
  • Version evidence remains narrow: 3.0/3.03 documentation and likely-version application use do not establish 3.5 or 3.52 support. Only named interpreter runs with inspected artifacts can establish native results.
  • Fixture selection: the application source is not a corpus fixture. Add only independently authored probes with exact syntax, a source-backed expected result, and a named target version. The existing corpus remains research_only; do not describe its metadata validator as a conformance runner.
