1. Scope and evidence policy

This document inventories Atari-specific GFA BASIC interfaces. It does not define portable GFA BASIC core semantics and does not claim that the project implements these interfaces.

The source describes Atari ST GFA BASIC V2.xx/V3.0. Do not transfer these declarations to Amiga GFA BASIC or later Atari releases without separate evidence.

Evidence labels:

  • Book-documented — the named interface or behavior appears in the identified book passage.
  • OCR/page check pending — exact spelling, signature, bit field, or offset needs comparison with the printed page image.
  • Runtime-unverified — no matching interpreter/TOS observation has been recorded.
  • Unsafe/OS-specific — direct memory, privilege, interrupt, disk, or hardware behavior must be isolated and disabled unless a machine/TOS profile explicitly supports it.

A book description is evidence of documented behavior, not proof that every TOS/GEM release behaves identically.

2. API profile boundary

The API profile includes interfaces that depend on Atari GEM, AES, VDI/GDOS, TOS, BIOS, GEMDOS, XBIOS or machine hardware. The source-language dialect/version, API profile, host and output target remain separate configuration dimensions.

Do not map these interfaces directly to Linux system calls or SDL3. A Linux implementation must emulate the documented Atari semantics through project-owned interfaces and an explicit target memory/device model.

4.1 GDOS installation and driver identifiers

GDOS is a resident GEM extension, not an unconditional part of the GFA BASIC runtime. In the book's setup it must be launched from the AUTO folder before normal system initialization and must find a valid ASSIGN.SYS at the boot volume root. The book distinguishes GDOS 1.1 from 1.8 and reports better reliability/performance for 1.8 based on the author's tests; this is historical source evidence, not a recommendation for every later GDOS clone. VQT_EXTENT and VQT_NAME are the two chapter functions explicitly stated to remain usable without GDOS. [pp. 499, 502]

The screen-resolution pseudo-drivers 02/03/04 in the example ASSIGN.SYS associate fonts with low/mid/high resolution; their drivers are expected in ROM. 4.4 Own fonts and direct system-font patching (unsafe research)

Pages 516–530 are not a general GDOS API. They present custom machine-code and BASIC techniques that patch TOS/GEM system-font pointers, reserve memory above HIMEM, install VBL interrupt routines, or reinterpret Degas/STAD font bitmaps. One supplied AUTO-folder program is explicitly limited to ROM-TOS dated 6 February 1986. Another routine warns that increasing BASIC memory with RESERVE while a font is active can overwrite font data; restoring original font pointers is necessary before leaving BASIC. [pp. 516–523]

The examples include direct writes to TOS/GEM system-font pointers at addresses around 0x607E and 0x2924. These are machine-/ROM-specific addresses, not portable API constants. One supplied AUTO-folder patch is explicitly limited to a ROM-TOS build dated 6 February 1986. [pp. 516–523]

The source describes these font data layouts:

  • Degas high-resolution font: 2,050 bytes (2-byte header plus 2,048 bytes for 128 glyphs × 16 scanlines).
  • STAD/OLIFONT high-resolution font: 4,096 bytes (256 glyphs × 16 scanlines).
  • 8×16 system font: 4,698 bytes (602-byte header plus 4,096 glyph bytes).

These are source-described formats; do not infer that every Atari font loader accepts them interchangeably. [pp. 528–530]

The later SUPER.FON example loads a bitmap-font file into caller-provided memory and draws each character through PUT operations; it is a program-level technique, not a VDI/GDOS workstation service. [pp. 524–530] These routines must remain classified as unsafe, ROM/TOS-specific research. Do not implement them as ordinary portable GFA built-ins or run them in the Linux compatibility runtime.

4.5 Cross-source validation: VDI, GDOS and workstation lifecycle

The chapter 17 inventory was compared with The Atari Compendium, chapter 7 (VDI), especially its VDI overview, workstation model, GDOS detection and bitmap-font sections. This is an independent Atari OS reference, not evidence that every GFA wrapper has been runtime-tested.

Confirmed architectural distinctions:

  • VDI is part of the TOS/GEM graphics environment; GDOS is optional. Atari systems with TOS in ROM provide a screen VDI driver. GDOS is a boot-loaded extension that supplies disk-loaded device drivers and additional fonts. Screen-only output using the system font does not inherently require GDOS. [Atari Compendium, ch. 7, “Overview”]
  • Physical and virtual workstations are different resources. A physical workstation initializes a device; only one physical workstation may be open for a given device at a time. Multiple virtual workstations can share that physical device while keeping separate drawing attributes. Every VDI call uses a workstation handle. [Atari Compendium, ch. 7, “VDI Workstations”]
  • The screen physical workstation is already initialized by AES. Its handle is obtained through graf_handle(). A screen virtual workstation is opened against that physical handle; the documented device ID is Getrez()+2. This is distinct from opening an external physical device through GDOS. [Atari Compendium, ch. 7, “Virtual Workstations”]
  • GDOS driver IDs are configuration IDs. The Compendium gives ranges 1–10 screen, 11–20 plotter, 21–30 printer, 31–40 metafile, 41–50 camera, 51–60 tablet and 61–70 memory; the selected ID corresponds to the ASSIGN.SYS entry. The book's sample IDs 01, 11, 21, 31, 41 and 51 fit those ranges. Do not treat these as guaranteed present devices or host device classes. [Atari Compendium, ch. 7, “Physical Workstations”]
  • Driver capability is not uniform. The Compendium warns that not every VDI function is supported by every driver and recommends inspecting workstation capability results. A printer or plotter profile must not inherit screen capabilities by default. [Atari Compendium, ch. 7, “Device Types vs. Required Functions”]
  • GDOS presence and GDOS version are separate questions. The Compendium describes a non-standard vq_gdos() query that distinguishes no GDOS, original GDOS 1.x, FONTGDOS and FSM/Speedo variants. The GFA GDOS? Boolean documented in the book only establishes its stated presence test; it must not be interpreted as a version detector. [Atari Compendium, ch. 7, “Determining the Version of GDOS Present”]
  • Additional bitmap fonts become available after vst_load_fonts(). The Compendium confirms that fonts listed for the device in ASSIGN.SYS are not exposed to applications until fonts are loaded. This corroborates the role of VST_LOAD_FONTS(0); it does not independently validate GFA's exact return value or unload semantics. [Atari Compendium, ch. 7, “Bitmap Fonts”]

Reconciliation and implementation implications:

  1. The book's V_OPNWK is the physical-workstation path for an ASSIGN.SYS/GDOS device. Keep the resident-GDOS precondition and invalid-driver crash warning attached to this wrapper.
  2. V_OPNVWK is the virtual-workstation path. Do not model it as equivalent to loading a GDOS driver; the screen's physical workstation is already provided by AES/TOS. The GFA wrapper's exact parameter adaptation remains book-scoped.
  3. Keep physical-device handle, virtual-workstation handle and GFA's internally managed screen handle distinct. A virtual workstation is a separate attribute context, not a new physical device.
  4. Treat the book's screen/plotter/printer/etc. IDs as examples from its ASSIGN.SYS configuration, not a promise that every installation has those drivers.
  5. Model GDOS as a runtime capability with a possible implementation/version identity. A Boolean GDOS? result is insufficient to claim compatibility with FONTGDOS, FSMGDOS or SpeedoGDOS extensions.
  6. Workstation support and individual VDI operation support must be capability-checked per driver. Do not silently emulate unsupported printer/plotter operations as screen output.

No GFA BASIC interpreter or Atari TOS runtime probe was performed. These cross-source confirmations validate the general VDI/GDOS architecture and resource distinctions, not every GFA wrapper signature or the book's reported buffer/error behavior.

Independent source: The Atari Compendium, Chapter 7 — VDI.

Important constraints:

  • Event manager calls can block while waiting for user input. Integrate them with the runtime event pump and timer model.
  • Form and menu calls require valid resource/object trees and correct object indices/flags.
  • Resource memory is allocated by GEM and must be released by the matching resource operation.
  • WIND_UPDATE locking must be paired correctly; incorrect pairing can block redraws by other applications/accessories.
  • The book reports unreliable behavior for some AES calls, including event recording and resource pointer adjustment. Record these as source-specific warnings pending TOS-version tests.

5.2 Cross-source validation: AES events, messages and windows

The chapter 18 AES catalogue was compared with The Atari Compendium, chapter 6 (AES), and Atari's GEM Programmer's Guide. These references corroborate the general AES contracts and expose one important source discrepancy.

EVNT_MULTI event mask

The GFA book's printed event table assigns bit 0 to both keyboard and timer events. The Compendium's AES reference defines the standard event mask as:

Event Standard AES mask
MU_KEYBD 0x01
MU_BUTTON 0x02
MU_M1 0x04
MU_M2 0x08
MU_MESAG 0x10
MU_TIMER 0x20

This independently confirms that the GFA book's timer-bit entry is inconsistent with the standard AES event mask: standard AES uses bit 5 (0x20), not bit 0. Preserve both pieces of evidence: the book's page-image-confirmed transcription remains a source defect, while the standard AES mask is the independently documented OS contract. Do not silently rewrite the book transcription or assume that the GFA wrapper forwards the mask unchanged without a runtime probe. [Atari Compendium, AES event library; book pp. 553–554]

Blocking and event-loop semantics

The Compendium describes the five basic event calls (message, button, keyboard, timer and mouse rectangle) as wait operations and EVNT_MULTI as the combined wait for any selected subset. Its typical GEM application uses an event/message loop. This supports treating GFA EVNT_* calls as blocking control-flow operations, not as non-blocking polling primitives. Exact GFA wrapper behavior, timer units and return values remain tied to the book's version-specific descriptions. [Atari Compendium, ch. 6, “Event Dispatcher”]

AES parameter-block ABI

The Compendium confirms that AES is called through TRAP #2 with magic value 0xC8 in D0 and a pointer to the AES parameter block in D1. The parameter block contains six pointers: CONTRL, GLOBAL, INTIN, INTOUT, ADDRIN and ADDROUT. The GEM Programmer's Guide independently describes the same six-pointer layout and the control array's opcode/count fields. This corroborates the 32-bit address elements and five-word control block already recorded in sections 7 and 7.1. [Atari Compendium, ch. 6, “AES Function Calling Procedure”; Atari GEM Programmer's Guide, Vol. 2]

Window ownership and redraw

The GEM Programmer's Guide identifies WIND_CREATE as allocating a window and returning its handle, WIND_OPEN as opening it, WIND_CLOSE as closing it, and WIND_DELETE as releasing the allocation. WIND_GET/WIND_SET query and change window state; WIND_UPDATE brackets application redraw/update operations. The Compendium's AES window model likewise uses messages for window-manager actions and requires the application to process redraw requests. This supports keeping create/open/close/delete as separate lifecycle operations and keeping redraw/message handling in the application event loop. [GEM Programmer's Guide, Vol. 2, §11.3; Atari Compendium, ch. 6]

Implementation implications

  1. Keep the GFA book's EVNT_MULTI transcription verbatim and mark the timer-bit conflict resolved at the standard AES layer (MU_TIMER = 0x20), pending a GFA wrapper probe.
  2. Model EVNT_* as potentially blocking operations that suspend BASIC execution until the selected event occurs.
  3. Keep the AES message buffer as a 16-byte message structure where the book specifies that size; its contents and lifetime must be associated with the event/message call.
  4. Model window creation, opening, closing and deletion as distinct state transitions; do not collapse them into one host window constructor/destructor.
  5. Treat WIND_UPDATE as a paired lock/unlock protocol and ensure cleanup on every exit path.
  6. Do not infer newer AES opcodes or version-specific calls from the generic Compendium list; each declaration still needs Atari GFA version evidence.

No GFA BASIC interpreter/TOS runtime probe was performed. The external references validate standard AES structure and behavior, not every GFA wrapper signature or the exact wrapper's event-mask conversion.

6.1 Cross-source validation: GEM structures and RSC format

The chapter 19 structures were compared with The Atari Compendium, chapter 6 (AES) and Appendix C (.RSC file format), plus Atari's GEM Programmer's Guide, Volume 2.

OBJECT record

The Compendium's OBJECT declaration confirms the 24-byte record: three 16-bit tree links, type/flags/state words, a 32-bit object-specific field and four 16-bit geometry values. It also confirms that object coordinates are relative to the parent object except for the root. This corroborates the book's 24-byte layout and parent/child navigation model. [Atari Compendium, ch. 6, “Objects”]

RSC header discrepancy and companion-disk evidence

The GFA book describes a 38-byte (19-word) RSC header:

  • offset 0: reserved word, always 1;
  • offsets 2–34: object/string/image/tree offsets and counts, ending with file length at 34;
  • offset 36: an additional zero end-marker word.

The Atari Compendium describes the original RSC header as 18 words (36 bytes):

  • offset 0: rsh_vrsn, with values 0 or 1 for the original format;
  • offsets 2–34: the object/string/image/tree offsets and counts, ending with rsh_rssize at 34;
  • no additional word at offset 36.

I inspected the three RSC resources included in the user-provided book companion diskette archive: ALERT.RSC, FORMULAR.RSC and MENU.RSC. All three begin with the standard 36-byte / 18-word header, have rsh_vrsn = 0 at offset 0, and begin their string area at offset 36. FORMULAR.RSC and MENU.RSC have rsh_rssize values equal to their physical file lengths (730 and 2,630 bytes). ALERT.RSC has rsh_rssize = 1,130 while its physical file length is 1,154 bytes, leaving a 24-byte trailer outside the declared resource size; this trailer is not yet explained. The companion BASIC listings AES_ALRT.LST, AES_FORM.LST and AES_MENU.LST explicitly load these corresponding resources with RSRC_LOAD, establishing that they are actual book-diskette examples used by its GFA programs.

This resolves the layout question for the supplied companion-disk resources: they use the classic 36-byte header, not the book's described 38-byte header. It does not prove which layout every GFA BASIC resource editor/compiler version can emit, because the archive does not establish the provenance of the resource-editor output. Retain the book's 38-byte table as a documented source discrepancy; use the 36-byte format for these verified fixtures. The Compendium also documents an extended RSC format on TOS 4.0+; do not assume the classic header is the only RSC variant. [Atari Compendium, Appendix C, “The .RSC File Format”]

Object flags and later AES extensions

The GFA book documents OB_FLAGS bits 0–8, including INDIRECT at bit 8, and six OB_STATE bits. The Compendium confirms those meanings but also documents additional OB_FLAGS bits 9–11 (3D appearance and submenu-related flags); several are explicitly available only from AES 3.4. It also documents G_CICON (object type 33) as available from AES 3.3. These are later AES extensions absent from the book's selected GFA BASIC V2.xx/V3.0 description. Keep them out of the 1988 GFA profile unless separate GFA-version evidence is found; they may belong in a separately versioned later-AES profile.

Nested structures

The Compendium and GEM Programmer's Guide corroborate the role of OBJECT.ob_spec as a type-dependent value/pointer and the use of TEDINFO, ICONBLK, BITBLK, APPLBLK and PARMBLK structures. The book's exact byte sizes remain source-backed and page-image-checked. Do not replace its ICONBLK 36-byte layout with a differently packed host-language structure; use explicit 68k-compatible field widths and offsets.

Implementation implications

  1. Parse the verified companion-disk fixtures with the classic 36-byte header; preserve the book's 38-byte description as a source discrepancy and investigate the unexplained 24-byte ALERT.RSC trailer.
  2. Parse RSC offsets as file-relative big-endian values; after loading, resolve/fix up pointers into a target-memory representation. Never cast file offsets directly to host pointers.
  3. Preserve the book's OB_FLAGS/OB_STATE subset for its declared dialect/version. Gate AES 3.3/3.4 additions behind explicit OS-profile metadata.
  4. Keep RSC version/format detection separate from the GFA BASIC language version.
  5. Treat RSC resource loading, pointer fixups and screen-coordinate conversion as GEM resource-manager behavior, not as generic object-tree construction.

No GFA resource-editor output or runtime parser test was available. The three companion-disk RSC fixtures establish the classic header for those examples, but not for every GFA resource-editor version.

8.9 Source consistency correction: GETDFREE buffer size

A line-by-line check of p. 614 confirms that GEMDOS(54) GETDFREE writes four 32-bit longwords, at buffer offsets +0, +4, +8 and +12. The required buffer is therefore 16 bytes, not 12 bytes. The printed prose calls it a “12-Byte-Puffer”, but the fourth field is explicitly placed at +12 and occupies another longword. This is a source-internal contradiction; the field layout determines the minimum size. Treat the phrase “12-byte buffer” as a likely book typo and preserve the discrepancy in evidence notes. No host implementation should allocate only 12 bytes.

8.10 Cross-reference validation against Atari OS documentation

The book's trap wrappers were cross-checked against Atari's A Hitchhiker's Guide to the BIOS, Rev. 1.1 (5 March 1990), and The Atari Compendium (GEMDOS/XBIOS chapters). These are independent Atari OS references; they do not prove that every GFA wrapper exposes every OS version's full contract.

  • BIOS uses TRAP #13; XBIOS uses TRAP #14; GEMDOS uses TRAP #1. Arguments are pushed on the 68k stack in reverse order, followed by the function opcode. The caller cleans the stack. The GFA wrapper hides this assembly-level calling sequence.
  • Atari's BIOS guide says XBIOS uses the same calling convention as BIOS. The Atari Compendium documents D0–D2 and A0–A2 as scratch registers for GEMDOS/XBIOS and says the function opcode on the stack is modified. The generic D0 return description in the GFA book is therefore insufficient as a complete ABI contract.
  • GEMDOS is not guaranteed re-entrant. BIOS and XBIOS have limited re-entrancy (the BIOS guide says three nested calls, without depth checking); this is not a promise that arbitrary callbacks or interrupt handlers may safely invoke them.
  • The Compendium recommends GEMDOS/VDI abstractions over XBIOS hardware calls where possible, and warns that hardware-specific calls may not transfer to later Atari systems.
  • The Atari BIOS Rev. 1.1 guide gives a concrete INITMOUS parameter block, whereas the GFA book explicitly does not provide a usable parameter layout. Keep the GFA-facing wrapper evidence and the OS-level structure as separate evidence records until the wrapper's marshaling is verified.
  • XBIOS opcode 11 is described as “no effect” by the GFA book. Atari's 1990 BIOS guide labels it “used-by-BIOS”; later Atari Compendium material identifies DBMSG as a debugger extension. Treat this as version/context-dependent, not as a stable no-op across all TOS variants.
  • The GFA book's BIOS(11) KBSHIFT description assigns bits 5–6 to Alt+ClrHome/Alt+Insert. Atari's BIOS Rev. 1.1 guide describes these bits as mouse-button states (and bit 7 as reserved). This is a concrete semantic discrepancy requiring an explicit source-version note; do not silently merge the tables.
